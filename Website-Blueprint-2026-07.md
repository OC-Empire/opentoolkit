# OpenToolkit Website Blueprint - 2026-07

## Current Truth

OpenToolkit has a real premise:

- large open-source tool index
- privacy / self-hosting / builder angle
- automation ambitions
- enough raw data to support something better than a directory

Current weakness:

- it still behaves like a catalog-first site
- it does not yet behave like a recommendation engine, stack builder, or community system

The opportunity is to turn it into a product with a flywheel.

---

## Product Thesis

OpenToolkit should become:

**the place where people assemble a sovereign software stack**

Not just:

**a page that lists 500 tools**

That means every part of the site should help users do one of four jobs:

1. Discover good tools quickly
2. Understand why a tool matters
3. Assemble multi-tool stacks
4. Contribute back into the system

---

## Site Model

### 1. Homepage

Purpose:

- express the mission
- let users enter by workflow
- highlight strong recommendations

Key blocks:

- Hero with clear thesis
- Quick modes
- Spotlight tools
- Stack recipes
- Product flywheel / contribution system

### 2. Tool Detail Pages

Purpose:

- convert a raw listing into a decision page

Each detail page should include:

- why this tool wins
- what it replaces
- best for
- platform coverage
- license / source / activity
- alternatives
- complements
- stack recipes containing it

### 3. Stack Recipe Pages

Purpose:

- make the site operational

Examples:

- Privacy starter stack
- De-Googled Android stack
- Local AI stack
- Self-host home stack
- Student knowledge stack
- Indie builder stack

Each recipe should include:

- outcome
- included tools
- role of each tool
- setup order
- optional upgrades

### 4. Submission + Review Layer

Purpose:

- make OpenToolkit alive

Needed:

- submit tool CTA
- review queue model
- verification badges
- “last reviewed” metadata
- automation pipeline visibility

### 5. Editorial Layer

Purpose:

- make OpenToolkit memorable

Potential formats:

- “Why this tool matters”
- “Cloud replacement guides”
- “Best open-source tools for X”
- “Regional toolkit” collections

---

## Release Batches

### Batch A - Information Architecture

- proper route model
- tool detail pages
- stack recipe route

- remove dead footer links

### Batch B - Decision System

- alternatives / complements
- “why this wins” logic
- scoring explanation
- compare-style shortlist for tools

### Batch C - Community + Automation

- GitHub-based submission workflow
- verified review states
- surfaced freshness metadata
- automation transparency page

### Batch D - Brand System

- stronger visual identity
- custom icons / illustrations
- richer motion
- storytelling / editorial polish

---

## What Makes It A Thing

OpenToolkit becomes a thing when it has all four:

1. Utility
2. Taste
3. Workflow
4. Community loop

Without utility, it is decoration.

Without taste, it is just another dump.

Without workflow, it is not operational.

Without community loop, it goes stale.

---

## Recommended Immediate Next Move

Build:

1. tool detail pages
2. stack recipe pages
3. real submit / contribute surface

That is the smallest set that changes OpenToolkit from “nice directory” into “emerging platform”.
